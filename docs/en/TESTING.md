# Automated testing

The repository keeps Node's built-in `node:test` runner. The supported local/CI test runtime is Node 22.12+ (22.x), 24.12+ (24.x), or 26.x with pnpm 12.16.1. The desktop tests use Node's type stripping and the Electron smoke also requires the built desktop and API; native dependency build approvals are pinned in `pnpm-workspace.yaml`. Install the workspace dependencies first:

```sh
pnpm install --frozen-lockfile
pnpm test:ci
```

`test:ci` is the pull-request gate: package-boundary checks, workspace build and typecheck, the existing package test suites, and a production-only packed SDK consumer check. The API keeps its existing serial `personal-api*.test.cjs` group and runs the remaining test files separately. The build, typecheck, test and boundary failures block the job. Dependency inventory and audit findings are emitted as sanitized evidence under ignored `coverage/test-evidence/`; known dependency advisories are reported, not silently waived or used as a pre-existing, permanently-red gate. Audit transport/schema failures still fail reporting.

The workflow runs stable `Core / Node 22.12.0`, `Core / Node 24.12.0`, and `Core / Node 26.13.0` checks. Desktop tests run on Linux and macOS with Node 24.12.0. The macOS Node 26.13.0 lane verifies Electron and the kernel SQLite native module, then runs the full desktop lane including the real Electron launch smoke. Nightly runs the same full PR regressions, ten deterministic host lifecycle repetitions, and external connector source compatibility. Manual workflow dispatch adds the SDK candidate matrix and packed consumer verification. A published GitHub release runs the packed core consumer lane against the released source SHA. All jobs use read-only repository permissions and upload short-lived JSON evidence containing source SHAs, lock/tarball SHA-512 hashes, package versions, and sanitized lane results.

Electron's installer uses the workspace override `extract-zip>yauzl: 3.4.0`: the older ZIP reader can leave extraction incomplete under Node 26 even though installation exits successfully. If a previous install reports `Electron uninstall` or lacks `electron/path.txt`, run `pnpm install --frozen-lockfile && pnpm rebuild electron`. Desktop `predev` executes Electron before building the API, so an incomplete installation fails early with this recovery command.

Useful focused commands:

```sh
pnpm test:host
REGENIC_SOAK_ITERATIONS=25 pnpm test:soak
pnpm test:consumer
pnpm test:desktop
pnpm test:report
pnpm test:compatibility -- --connector dingtalk --sdk stable
pnpm test:compatibility -- --connector dingtalk --sdk candidate
```

The real-host executor tests use the actual API, Nest host, SQLite authority store, driver/executor registries, and installation lifecycle. A temporary child-process JSON-RPC endpoint stands in only for the external executor. Barriers establish ordering; no sleeps determine lifecycle assertions. Each test uses temporary HOME/config/data/database/blob directories and an OS-assigned local port, closes the owned server and process, checks the port is closed, and removes its fixture. Cases cover metadata-only reads without activation, multiple org/install bindings, recipe pin override resistance, enable/disable/reconfigure/delete, persisted restart without old-generation resurrection, cross-install/cross-org rejection, admitted work drain, and process cleanup. Existing durable reply recovery tests cover unknown delivery outcomes and refusal to replay.

The API process-restart cases in `apps/api/test/personal-api-work.test.cjs` cover SQLite and, when `TEST_DATABASE_URL` is set, PostgreSQL. The PostgreSQL cases require `CREATEDB` or a superuser on a test server: each case creates a randomly named disposable database because API background-leader locks are database-scoped, not schema-scoped. Credentials reach API children only through their isolated environment. The tests kill the owned API processes, wait for their database sessions to close, and drop only the databases they successfully created; they never terminate unrelated sessions or restart PostgreSQL. Use a test server and credentials authorized for this temporary database lifecycle. The in-flight cases wait for the real cancellation lease to expire before recovery, without shortening production timeouts.

The acknowledgment crash case also holds the real HTTP response after the acknowledgment endpoint has returned from its Authority transaction. A separate store connection must observe the committed result before the API process is SIGKILLed; after restart, replaying the identical `command_id` must return the acknowledged run without another WorkItem version change, Run, delivery, or cancellation job. This is a response-loss-after-commit test, not a crash during an uncommitted transaction.

For failed-result acknowledgment, an additional SQLite process-restart case keeps the recipe enabled and seeds a failure older than the maximum automatic retry backoff, so a restart scan is genuinely eligible to retry it. The API commits acknowledgment and is killed before the held HTTP response is released. The restarted API is not maintenance-paused: the test replays the same command and runs a normal work tick, then compares the full persisted snapshot. The acknowledged failed Run must remain the only Run, with no new delivery or cancellation job, proving automatic retry does not restart an explicitly reviewed failure.

An API-level manual retry case covers the complementary user intent: after acknowledging a failed Run, an explicit start command may create one new Run even with the Recipe disabled. The new reservation clears the old `acknowledged_run_id`, the original failed Run remains unchanged, and replaying the start command returns the same Run without creating a second DSH session. If the original trigger is still the source head and was moved out of `current_work` by that acknowledgment, the same reservation restores that exact trigger to `current_work` and records the transition atomically; stale or superseded triggers are not revived. Replaying the old acknowledgment command afterward returns its original result without restoring the old acknowledgment marker or changing the new Run.

The Domain regression exercises the same transition through `IngestionService` and `MemoryAuthorityStore`, including the failure acknowledgment, manual reservation, restored disposition, and `current_work_changed` lifecycle event.

The required-write-back API cases combine real SQLite ingestion and lifecycle commands, the production delivery flusher, a synthetic driver with a loopback HTTP sender, and public Inbox/acknowledgment/retry/reconciliation endpoints. Execution completion is supplied through `commitWorkObservation`; background work is maintenance-paused and the flusher is invoked directly. Pending, explicitly rejected, and uncertain deliveries must remain visible, and marking them read must not acknowledge the result. Rejected and uncertain deliveries retain `waiting_you` attention even after reading. For unknown acceptance, the sender closes the real HTTP connection without returning a receipt; another flush and a direct retry must not resend. Human reconciliation as `sent` settles the original delivery without another send or a fabricated channel receipt; reconciliation as `not_sent` permits one resend with the original destination and idempotency key. The synthetic destination records exactly one delivered result in each case. All three paths run under both legacy acknowledgment and frozen automatic completion policy v1: legacy attempts need exact result acknowledgment, while v1 automatically retires the exact trigger and folds after settlement without fabricating user acknowledgment. Neither policy folds the destination. Command replay cannot resend, and a new request unfolds the source without being hidden by replay of the old acknowledgment. This is SQLite API composition coverage, not a real-executor, automatic-scheduler, or Electron write-back acceptance.

The real Electron smoke also clicks the failed-result acknowledgment button and starts the reviewed failure. The real API reservation must freeze completion policy v1 on the new Run. Successful execution without required write-back then automatically folds the source, removes obsolete renderer actions, and leaves no `needs_ack` reminder without fabricating user acknowledgment. Its loopback HTTP executor must receive exactly one start request; the original failed Run remains unchanged and no extra Run, delivery, or cancellation job is created.

SQLite and writer-RPC automatic completion tests cover successful no-write-back closure and restart persistence, required delivery rejection/uncertainty and sent reconciliation, failures and other current work, manual show intent, new-work reopening, and rollback if completion audit insertion fails. Upgrade tests reopen a schema-73 database with its existing work intact, verify schema 74 preserves historical snapshots and NULL policy versions, then complete the old run after upgrade and acknowledge it after another restart. New user Runs started through the single-instance SQLite API/Electron runtime freeze `completion_policy_version: 1`; system work and PostgreSQL runtime reservations do not enable it. PostgreSQL has matching schema/read/write support only; it is not claimed as automatic-policy acceptance.

The SQLite pre-commit acknowledgment case uses a test-only Node preload in the API's SQLite writer worker. It blocks only after inserting the target command's final `work_acknowledged` audit row, while the enclosing transaction is still uncommitted. An independent Authority reader must see the complete pre-request snapshot during the block and after SIGKILLing the API also terminates the worker; a restarted API must apply the same command exactly once. This verifies SQLite read isolation and rollback after process death; it does not claim PostgreSQL pre-commit crash coverage.

The API also injects a SQLite trigger failure on the final `work_acknowledged` audit insert. The real endpoint must return HTTP 500, leave every earlier transaction update rolled back, and persist no command audit; after removing the trigger, replaying the same command must succeed exactly once. This is SQLite-only SQL-failure coverage.

`scripts/testing/connectors.json` records exact default-branch source SHAs, the frozen-source SDK expectation, and the actual contract range for Slack, WhatsApp, DingTalk, WeCom, Telegram, Discord, Claude Code, and GitHub Copilot. Both modes frozen-install, build, typecheck, and test the source against its lockfile dependencies. Required link scripts receive a checkout-shaped SDK layout pointing to those same frozen-installed packages, not to the candidate core. DingTalk/WeCom source stages therefore use contract 0.2.0 even in candidate mode; Claude/Copilot source stages use registry contract 0.3.0. Candidate lanes then pack the current core SDK as `.tgz`, install into a canonical-path consumer with its own manifest, validate the exact top-level npm lock entry's local-tarball resolution and SHA-512 integrity, and prove the plugin load resolves the candidate contract by real path and version. A same-version registry package cannot satisfy this identity check. Candidate source compilation is not claimed.

Consumer compatibility mode is explicit per connector:

- `packed-npm`: pack the connector and install it together with the stable SDK packages or candidate SDK `.tgz` files into an isolated consumer. The actual compiled API plugin loader loads the package and validates its declared contributions against the core protocol boundary; core and plugin contract modules are not required to share a physical instance.
- `clone-root-core-loader` (GitHub Copilot): preserve its source-root frozen install/build/typecheck/test and audit, verify Zod 4.6.7 from the actual Copilot SDK entry's resolution, then load the built plugin through the compiled API loader without activation. Candidate mode supplies packed candidate SDK packages via an isolated module-resolution overlay. The core and cloned connector intentionally have separate dependency roots.

For Copilot specifically, the Zod 4.6.7 override is validated both as source-root configuration and by the **actual Zod package resolved from the Copilot SDK entry point**. This does not claim arbitrary downstream tarball consumers inherit that override. No connector is tested by silently overriding its declared contract range.

The desktop lane runs existing isolated unit tests, the Electron production build, and the real Electron semantic smoke with a synthetic local embedding HTTP server and a disposable database/profile. Lifecycle checks install a loopback HTTP executor through the real API, open each task while its run is active, wait for the read cursor to commit, then release a completed or failed status. This avoids conflating the existing read-to-review behavior with the explicit result/failure acknowledgment buttons. Real background supervision and renderer clicks must confirm the exact runs without changing their terminal facts, duplicating runs, or creating deliveries/cancellation jobs. The checks also verify reviewed state and the hidden-list projection after the desktop's permission controls restart its owned API kernel and the renderer is reloaded.

Required-write-back checks additionally install a synthetic sender plugin through the real connector API. Normal background supervision and delivery flushing produce an explicit rejection or uncertain acceptance when the loopback sender closes its HTTP connection without a receipt. Real renderer retry and sent/not-sent reconciliation buttons must settle the original delivery with its frozen destination and idempotency key, recording exactly one delivered result. Reading cannot dismiss the delivery reminder. With frozen automatic policy v1, settlement itself atomically retires the exact trigger and folds only the source, not the destination; no result acknowledgment click or fabricated user acknowledgment is required. Completed results remain accessible on the hidden list without an acknowledgment action. The checks wait for renderer completion projections and saved list preferences before issuing the next action or reloading, rather than treating a database commit as a completed UI refresh.

The main-flow checks also quit Electron normally, verify clean exit and store-lock release, then relaunch the same profile and database. All four automatically completed results must remain hidden and quiet, with unchanged terminal Runs, trigger dispositions and delivery ledgers. Results reopen from the real hidden list without an acknowledgment action, and restart must not resend or rerun completed work. Existing read-to-review behavior may record a real acknowledgment for the exact current Run when a completed result is reopened; automatic completion itself must not fabricate that acknowledgment.

For SQLite desktop main-flow acceptance without the two full-process crash checks, run `node apps/desktop/scripts/semantic-electron-smoke.cjs --skip-crash` from the repository root after the usual builds. This command passed all three delivery recovery paths, normal same-profile full-process restart, and clean Electron shutdown on macOS. It does not replace the default smoke: the latest default run stopped at the existing in-flight acknowledgment crash recovery row lookup, so full crash acceptance is not claimed for this run. The executor and sender remain loopback substitutes, not real external systems; PostgreSQL and deployment acceptance are outside this evidence.

On macOS and Linux, the smoke additionally stops the synthetic managed model, identifies the API kernel by its direct parent PID and exact command, and sends SIGKILL to the owned Electron process only. The API sidecar observes that its recorded parent PID has changed, closes its Nest application and exits; the test verifies the real stale store lock and database remain untouched. It then launches Electron again with the same profile and data paths. The new desktop must reclaim the stale lock, preserve the exact reviewed runs and versions, reopen the completed result from the hidden list without another acknowledgment action, and keep the reviewed failure outside current-work lists without changing its visibility preference. The restarted desktop must then quit cleanly and release its lock. Windows explicitly skips this POSIX process-inspection slice. This covers Electron loss after acknowledgment commits and orderly exit of its owned kernel; the in-flight acknowledgment case below is SQLite-only, and PostgreSQL desktop deployment remains untested.

The smoke also clicks a real renderer acknowledgment button and pauses the API's SQLite writer after the final audit insert but before transaction commit. It confirms an independent reader still sees the old snapshot, then SIGKILLs Electron while the request is in flight. If `app.close()` cannot drain the blocked writer, the sidecar exits after a five-second shutdown deadline so SQLite rolls back the transaction instead of leaving an orphan kernel. The same profile must restart with the result still unacknowledged, allow one successful retry, and preserve the exact run without extra delivery or cancellation work. This in-flight UI case is SQLite-only.

The lane does not log in to any account, call an external model, send messages, or start a real agent. Linux runs under Xvfb; its ephemeral CI runner configures Electron's `chrome-sandbox` helper as root-owned mode 4755 before launching, rather than disabling the Chromium sandbox. Local Linux runs require the corresponding Electron sandbox setup. The CI macOS lane provides the native macOS run.

`pnpm test:tooling` also runs offline npm pack/install/lock regressions and independent subprocess tests for signal-killed, already-exited and failed-exit smoke children. Smoke failure is marked nonzero before asynchronous cleanup; shutdown reuses the originally registered exit promise with a bounded kill wait.

Live/account validation is intentionally manual and opt-in. Before doing it, a maintainer must select a dedicated test account/tenant and confirm ownership, obtain scoped credentials through the normal secret store, understand whether a test can create or send real content, and explicitly approve the operation. Never put credentials in workflow variables, fixtures, logs, or artifacts. CI does not contain a live-test switch and does not perform those actions.
