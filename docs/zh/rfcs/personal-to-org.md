# 从个人库到组织权威事件

- **English:** [../../en/rfcs/personal-to-org.md](../../en/rfcs/personal-to-org.md)
- **状态：** 产品架构草稿（未编号）
- **依赖：** RFC 0005（Event/Blob）、0002（图谱）、0006（ACL）、0007（蒸馏）
- **产品：** [产品定位](../PRODUCT.md)

## 1. 要解决什么

个人版已经能服务一个使用者的完整加工流程。组织版要把多个人的数据合在一起，同时避免：

- 把各人手里的副本都当成不同事实（简单合并会爆炸）；  
- 把个人侧的 AI 标签直接升成组织事实；  
- 借蒸馏任务扩大可见范围。

## 2. 怎么合

```text
渠道消息（推送或拉取）
  → 个人 Event（可带个人加工标签）
  → [工作范围授权 / 显式同意]
  → 组织权威 Event（一条物理事实）
       + 各人视角（Projection）
  → 组织 Digest / Claim / Snapshot（组织任务 + visible()）
```

| 概念 | 含义 |
| --- | --- |
| 个人 Event | 某人对该消息的视角，可带优先级、「该知道」、未回复等标签 |
| 权威 Event | 客观事实：谁、何时、说了什么、线程、是否撤回 |
| 视角（Projection） | 谁接入的、当时能看见什么、个人标签是什么 |
| 组织 Digest | 只由组织侧管道产出（RFC 0007）；不得原样拷贝个人标签 |

## 3. 如何认定「同一条」

1. 优先用 `(org_id, source, external_id)` 跨人对齐。  
2. 没有稳定外部 id 时，再用 `(org_id, content_hash, 时间桶, 规范化后的行为人)`。  
3. Blob 仍按 `content_hash` 内容寻址；组织侧只保留或引用一份。  
4. 行为人经身份映射表对齐；对不上的标为未解析，禁止硬合并。

## 4. 客观与主观分开

| 类别 | 以谁为准 | 例子 |
| --- | --- | --- |
| 客观 | 权威 Event | 正文 hash、源时间、线程 id、撤回标记 |
| 主观 | 个人视角 | 分级、该知道、未回复排序、个人摘要 |

组织侧蒸馏可以**参考**主观标签，但必须在 `visible(job)` 约束下重新计算，
并写成带组织出处的 Digest / Claim。

## 5. 同意与范围

- 默认只汇聚绑定了工作场景的连接器或频道。  
- 个人私聊默认不进组织，除非当事人明确打开。  
- 按连接器或权限域分别授权。  
- 组织热库优先存薄 Event 与 hash；正文按需读取，并留下审计。

## 6. 冲突怎么处理

- 正文 hash 相同 → 一条权威 Event，多条个人视角。  
- 编辑或撤回 → 走版本或「已被取代」链，禁止直接覆盖。  
- 「是否未回复」默认仍是个人状态；若源系统自有共享状态（如工单状态），以源系统为准。

## 7. 验收

1. 两人各自接入同一条飞书消息 → 组织侧一条权威 Event、两条视角。  
2. 没有组织侧加工任务时，个人的「该知道」不会变成组织 Claim。  
3. 某人关掉个人远端历史，不影响其他已授权汇聚的同事完成对齐。
