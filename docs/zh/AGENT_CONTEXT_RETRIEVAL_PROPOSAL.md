## 1. 决策摘要

**最高优先级不是改善搜索结果展示，而是打通“客户问题补全 → Cursor 业务查询 → 回复核验”的客服任务闭环。**

以“上次选中的 6 位都还没回复吗？”为核心验收例：系统应确定客户、项目、批次、已确认名单和“回复”的业务含义，再查每位对象的实际状态。仅检索到相似消息、带出更多前后文或给 Cursor 一段流畅摘要，都不算完成。

检索层仍推荐“小块定位、对话段阅读、有预算组装、按需续读”，而不是纯 grep 或全会话灌入。
复用关键词与向量召回、ContextEngine 授权/生命周期/预算/snapshot；增加问题补全、业务身份映射和双来源证据核验，不另建一套上下文权威存储。

职责分工：

- **Regenic：** 验证发起消息与业务范围，提供检索/续读、证据绑定、任务状态和客户可见性检查。
- **Cursor / Agent：** 在限定预算内提出指代解释、继续搜索和只读查询计划，使用已配置的业务工具获取事实并生成草稿。模型提出的解释是候选，不自动成为事实或权限。
- **受控业务查询工具：** 强制执行数据范围、只读权限、参数校验和结果出处，不能只依赖 prompt 约束。
- **客服人员：** 处理未解歧义或冲突，确认首版对外回复；不是要求人工替系统完成所有正常检索。

检索支撑保留两个逻辑工具：

1. `search_context`：定位并自动展开，返回预算内的对话证据包。
2. `read_context`：沿返回的句柄继续读对话或超长消息，不接受任意本地文件路径。

在工具之上增加版本化的 **CustomerTaskBrief（客服问题说明）**，由原始问题、已核验解释、对象集合、待查字段和证据引用组成。
业务工具返回 **BusinessEvidence（业务查询证据）**，经覆盖、时效和冲突检查后才生成草稿。两者都是有出处的派生记录，不是新的事实来源。

工具名是建议名。优先复用现有个人 API / CLI；**Cursor 实际能调用的接入方式是 P0 前置项**。
若目标 Cursor 环境只能通过 MCP 使用这些工具，则最小 MCP 适配属于 P0；
通用多 Agent 适配平台、虚拟文件系统和搜索 UI 美化后置，不能阻挡主场景。

### 优先级与完成定义

| 优先级 | 范围 | 完成条件 |
| --- | --- | --- |
| **P0** | 发起问题绑定、上下文补全、批次/名单解析、受控身份查找与状态查询、覆盖核验、可见性处理、人工确认草稿、真实 Cursor 闭环验收 | 正常客服用例能正确给出有证据的答复；歧义/缺口/冲突用例正确澄清或转人工；不能只用检索 demo 或 mock 数据库宣告完成 |
| P1 | 扩展更多业务问法/渠道、提高大库性能、客服查看证据与诊断体验 | 不改变 P0 边界并通过回归 |
| P2 | 通用文件视图、生成式摘要导航、ANN、非必要 reranker/多 Agent 平台 | 有实际收益证据后再评估 |

本方案最高优先级是功能交付目标，不是绕过权限、数据治理或人工发送确认的理由。

### 本方案不承诺什么

- 不能保证模型回答一定正确；可保证的重点是证据绑定、明确边界、预算和可继续读取。
- 不能保证一次工具调用返回整个源平台会话；完整性受同步范围、授权、文本可用性和预算限制。
- 不把“全部向量已索引”“读到本地末尾”或“未检出反例”解释为“事实已完整”。
- 不在首版实现组织多租户 ACL、任意历史/as-of 阅读、图片理解、自动抓取未同步源历史或生成式长期记忆。
- 不假定 Cursor 已经具备数据库访问能力、业务 schema 已知或客户可见性规则已经存在；必须先验证这些接入合同。
- 不自动更新业务数据库、承诺交期/报价或自动向客户发送消息。首版 P0 是查询并生成可审核回复，不是无人值守客服。

## 2. 核心场景与成功体验

### 2.1 主验收例：上次选中的 6 位

客户问题：

> 上次选中的 6 位都还没回复吗？

系统必须补全如下信息，不能直接把这句话作为全库相似度搜索后生成答案：

| 待确定项 | 有效依据 | 不允许的推断 |
| --- | --- | --- |
| 客户、项目 | 发起会话的受信任绑定、可验证项目引用、必要时澄清 | 同一群里的所有消息都属于同一项目 |
| “上次”对应批次 | 最终名单确认记录、批次 ID、确认时间与后续更正 | 时间最近或相似度最高的一条就是目标批次 |
| 选中的对象集合 | 已确认名单及增补/替换链；对象逐一有出处 | 搜索到六个名字就凑成完整名单 |
| “回复”的业务含义 | 问题与业务字段定义：邀约回复、合作确认、报价或交付 | 未交视频等于未回复，或谈价等于确认合作 |
| 查询时间 | 客户问的是当前进展还是某个业务时点 | 旧聊天中的状态就是现在状态 |
| 对外可见范围 | 该客户、项目和字段的业务规则 | 客服能查到的内容都可以发给客户 |

用户示例里的“执行中的几位”和“上次选中的 6 位”只视为待解释的两组指代，
不能因为同屏就认为是同一批人。截图不足以恢复完整六人名单或当前状态；
实现评测使用独立构造的事实 fixture，不从截图补造名单和 ID。

### 2.2 正常成功路径与保守分支

正常路径：系统找出已确认的批次和六人名单，逐一解析业务 ID，Cursor 查询六人的相关状态，
得到诸如“已回复但未合作 / 已明确拒绝 / 仍待回复”等业务定义下的结果，
核对全部覆盖后生成带内部证据的客户回复草稿。这里的状态仅为示例，不是截图中六人的实际情况。

至少需要同时覆盖这些分支：

- 两个可能的“上次”：先在范围内补证，仍无法区分则请求批次确认。
- 已确认六人但数据库只匹配五人：明确一位身份未匹配；不能说这位“未回复”。
- 原名单有一位后来被替换：按目标批次在查询时点的有效成员查询，保留变更依据。
- 数据库与后续聊天冲突：按字段权威规则和时效处理，无法确定则提示人工核实。
- 状态记录不存在、查询失败、权限不足：与明确的 `pending_response` 分开，不将技术缺口转成业务结论。
- 内部备注或报价差额：只能作为授权分析材料，不能默认写入客户回复。

**P0 成功是恢复问题语义并完成正确的业务查询和回复核验，不是每个问题都强行给出确定答案。**
正常可解用例也不能一律转人工来“规避错误”，验收须同时测量解决率和不必要澄清率。

### 2.3 对话展开是支撑能力

以下通用例保留为指代与后续变更的组件测试：

示例：

```text
09:00 甲：方案 A 本周上线；方案 B 下周上线，但支持离线。
09:02 乙：客户必须要离线能力。
09:03 甲：那就按第二个方案。
次日  丙：客户取消离线需求，改回方案 A，周五上线。
```

只召回“第二个方案”会缺少指代；只展开附近两条仍可能漏掉次日变更。正确体验不是机械扩长 snippet，而是：

- 初次返回命中及解释它所需的讨论；
- 表明后续还有未读内容；
- 对“最终决定/现在怎么安排”类问题，Agent 能继续检查后续消息；
- 回答引用实际支持结论的消息；证据不足时说明范围，不臆造最终结论。

“尽量完整”在本方案中指 **客服任务所需的证据闭合**：对象集合可确定、待查字段明确、
事实来源与时效可查、关键变更被处理，剩余缺口可见。它不等于“聊天记录越多越好”。

## 3. 现状核对与复用边界

| 当前实现 | 可复用能力 | 必须补齐的部分 |
| --- | --- | --- |
| [ContextSearcher](../../packages/context-engine/src/context-searcher.ts) | 混合检索 trace、来源引用、coverage | 现有请求为 `display`，预算 8000、Event 输出、最多 480 字符 snippet；不是 Agent 完整证据接口 |
| [DeterministicContextEngine](../../packages/context-engine/src/deterministic-context-engine.ts) | 授权、生命周期、融合、预算、不可变 snapshot/bundle | 尚无对话窗口组装；现有预算按候选逐项选择，可能拆散语义单元 |
| [Event retriever](../../packages/context-engine/src/deterministic-event-retriever.ts) | Event/conversation anchors、来源/会话/时间过滤 | conversation anchor 是筛选，不是“围绕命中补前后文”；重新带原 query 检索会继续过滤掉无关键词的回答 |
| [Authority context source](../../packages/context-engine/src/authority-context-source.ts) | 当前 Event、正文物化、hash/编码校验 | 当前走完整 context read；没有已证明可扩展的邻接分页读取能力 |
| [ContextQuestionAnswerer](../../packages/context-engine/src/context-question-answerer.ts) | 从 bundle 回答、证据视为不可信数据、引用绑定验证 | 引用存在不等于结论被证据支持；目前没有自动续读循环 |
| [PersonalContextService](../../apps/api/src/personal-context.service.ts) | assemble/search/source/ask 等受保护入口 | `search/source` 只取一个当前 Event；应新增 reasoning 用途入口，而非提升旧 display 快照权限 |
| [个人 policy](../../packages/context-engine/src/personal-context-policy.ts) | 服务端绑定个人 owner/principal | 这是个人边界，不等于已实现组织级细粒度 ACL 或 Agent 独立权限系统 |
| [CLI context 命令](../../packages/local-cli/src/commands/context.ts) | 本地 search/assemble/ask 基础 | 为运行中内核提供同语义的工具调用；不要让 Agent 另起进程争用正在打开的库 |

以上能力不证明 Cursor 已经接通目标业务数据库，也不证明存在客户/项目/批次到业务 ID 的可靠映射。
现有 Cursor 消息接入与本方案的“受控业务查询 + 结果核验”是不同能力，不能以能发送 prompt 代替接入验收。

### 3.1 不能忽略的消息关系问题

[IngestRecord](../../packages/connector-contract/src/ingest.ts) 已有 `thread`、`parent_external_id`，
但不能据此假定这些关系已经完整持久化并可供 Context 读取。
[当前上下文元数据映射](../../packages/domain/src/ingestion-service.ts) 主要保存会话、actor、scope 等，
需要逐渠道核对原生回复关系如何进入可查询的投影。

**Event 的 `parent_event_id` 用于 revise/tombstone 生命周期，不是“回复了哪条聊天消息”。**
误用它会把旧版本当作前文，甚至重新引入被替代内容。

会话身份应复用现有 canonical identity，并核对 connector/installation 的命名空间。
不要用标题、裸 external ID、Event ID 前缀或临时拼接字符串重新猜会话。

### 3.2 不是在现有搜索结果后简单追加消息

当前搜索是先 `assemble`，再产生 snippet；到这一层时已有候选因预算被排除。
若只在 API 返回结果后做 N+1 次收件箱读取：

- 无法统一控制总预算与去重；
- 容易混用不同读取时点；
- 可能绕过 reasoning 用途、current 检查或快照绑定；
- 无关键词的邻近消息仍可能被二次检索过滤。

因此应在 **授权后的种子召回与最终预算装配之间** 增加展开步骤，
而不是把 display 搜索快照直接交给 Agent。

## 4. 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| Agent 直接 grep 数据库/Blob 导出 | 对精确字符串直观，容易原型化 | 不懂生命周期、授权、会话边界和引用；导出易过时；语义改写召回差 | 不作为产品主链路 |
| 增大 snippet / top-k | 改动少 | 更多孤立片段，不自动补齐指代或结论；增加噪声和 token | 不能解决核心问题 |
| 整个会话一个向量，命中即返回全量 | 小会话容易理解 | 大群/长 Agent session 超预算，多话题相互稀释，重索引成本高 | 不作为默认策略 |
| 完全由 Agent 逐条 search/read | 灵活 | 调用多、行为不稳定，Agent 反复拼接，难统一保证证据闭合 | 保留续读，不把全部工作交给 Agent |
| 混合召回 + 服务端展开 + Agent 续读 | 兼顾语义、精确检索、成本与可追溯性 | 需要关系、预算和续读协议 | **首选** |
| 先生成摘要，Agent 只读摘要 | 节省 token | 丢失限定条件、过时风险，可能生成错误事实 | 后续可选导航层，不能替代原文 |

### grep/read 思路如何保留

- 精确名称、错误码、单号：保留词法/精确查询路径，与向量互补。
- 命中后阅读附近内容：由 `read_context` 实现，返回有权限边界的结构化对话。
- 初版不开放任意 regex、shell 或磁盘路径；如有必要，后续增加受限 literal search。
- 文件系统式体验只能是授权快照/会话视图的适配层，虚拟路径不是权限凭据，也不是底层文件地址。

## 5. 目标架构

```text
客户原始问题 + 发起消息/会话 + 可信授权与客户范围
                 |
      建立客服任务；检查 Cursor / 业务工具能力
                 |
      问题补全循环（Cursor 提出解释，Regenic 校验证据）
      - 识别“上次 / 几位 / 回复”的未解含义
      - 当前回复链 → 当前会话 → 有关联依据的项目会话
      - search_context / read_context 补证，检查后续变更
                 |
      CustomerTaskBrief：批次、名单、待查字段、证据与缺口
                 |
      受控身份查找 → Cursor 按已核验 ID 执行业务只读查询
                 |
      BusinessEvidence：对象、结果状态、来源、时点与完整性
                 |
      覆盖 / 权威来源 / 时效 / 冲突 / 客户可见性核验
                 |
      回复草稿 + 内部引用 → 人工确认 → 既有发送路径

任一步关键依据不足 → 有限补证 / 最小澄清 / 转人工，不猜测补齐
```

检索底层继续使用“授权 current 视图 → hybrid 种子 → 对话展开 → 预算 bundle/snapshot”。
确定性展开不依赖回答生成模型，不要求更换 Embedding 模型；问题理解与检索计划可由 Cursor 承担。
**Cursor 的解释、业务 ID 和状态判断必须有来源约束，模型信心分数不能替代证据。**

### 5.1 问题补全：找什么比多返回什么更重要

把待补全信息记录为槽位：客户/项目、事项/批次、对象集合、状态语义、时间范围。
每项处于 `unresolved / candidate / verified / conflicting` 之一，只有绑定证据且满足校验规则后才可 verified。
“六位”是用户提供的核对线索，不是允许程序补足六条结果的约束。

检索计划围绕缺口逐步形成，不是固定把原问题改写三遍：

1. 解析发起消息的真实引用和当前讨论，优先确定项目、状态字段含义。
2. 在当前会话寻找名单确认、选人结论或批次引用；扩展时读完整相关讨论。
3. 为候选批次查找替换、作废、补选等后续记录；相关状态变化也可能来自业务数据库。
4. 已有可靠项目关联时才跨会话补证；没有关联不以全库同名搜索自动突破范围。
5. 匹配到多个批次或实体时保留候选及依据；继续有界核验，无法排除则澄清。

客户、项目和权限范围由可信绑定限制；模型提出的项目只是候选，不自动改变授权过滤。
如进入的是未绑定项目的会话，可在已授权目录内进行范围解析；未确定前禁止做跨客户的广泛状态查询。

### 5.2 业务身份与字段语义

优先使用来源系统 ID、稳定频道/主页 ID、项目/批次关联和显式映射表。
昵称、别名、链接可以作为查询线索，但必须保存映射来源和适用范围；同名多匹配不能自动取第一条。

对象集合须保留名单确认引用、成员逐项来源与有效时间。名单没有闭合时允许返回已知部分，
但不得把“不在返回列表中”推断为“不在名单中”。数据库也可提供权威批次名单，
不要求所有身份事实都从聊天推导。

业务字段字典应明确“邀约已回复”“合作已确认”“报价中”“已交付”的含义、权威数据源、
更新时间字段及客户可见性。首版只接入完成该主场景所需的字段，不建设泛化全业务本体。

### 5.3 业务查询边界与接入前置

“数据库”在这里指业务事实库，不是 Regenic 的 Event/Blob 存储。
Cursor 必须使用已授权的只读业务工具，工具层强制 tenant/customer/project 范围，
优先参数化的批次/实体查询，不把从聊天得到的任意 SQL 直接执行。
查询时限、返回行数、字段白名单、分页完成状态均需有界。

可在最终名单确定前调用受限的**身份/批次查找**工具辅助消歧；
只有范围与目标已核验后才执行目标状态查询。两个阶段都不能授权全库枚举。

实施前先核实并记录：

- 目标 Cursor 的运行方式及可调用工具通道；能否在同一任务中检索、续读、业务查询和返回结果。
- 首个业务数据源、测试环境、schema/视图、租户与项目字段、身份键和只读凭据管理。
- 必要字段的权威来源、新鲜度要求、历史查询能力、客户可见规则与人工确认入口。
- 经授权的真实业务测试样本或等价验收库；不能擅自使用现有个人数据或生产凭据。

上述信息缺失时标为接入阻塞，使用 synthetic fixture 开发合同，
但不得声称已经覆盖真实客服场景。个人 Context policy 不能代替业务库的客户隔离。

### 5.4 阶段产物与失败状态

以一个 `task_id` 关联原问题、brief 版本、Context snapshots、业务查询结果和草稿。
状态依次为 `resolving_context → ready_for_query → querying → verifying → draft_ready → awaiting_review`；
补证可回到 resolving_context，`needs_clarification / needs_human / failed` 是显式分支。

`ready_for_query` 只表明任务范围与必要参数具备依据，不保证业务数据完整。
原问题或批次名单变化后生成新 brief 版本，旧查询和草稿必须重新核验，不能继续沿用。
模型不得通过自报 `verified=true` 绕过这些转换条件。

## 6. 支撑 P0 的检索与展开策略

### 6.1 定位种子

1. 以发起消息、会话和已核验业务范围为锚点，复用授权域内 hybrid/lexical 检索，不先全局搜索再过滤。
2. 保留命中的 Event/hash、匹配段位置和检索 trace；以当前 Event 身份去重。
3. 对同一会话中高度重叠的命中聚合，避免一个长会话占满所有候选。
4. 在已核验业务关联范围内保留跨会话候选，后续按预算选择；不能只返回排名第一会话并称其为完整答案。

初始实验参数建议：候选种子最多 20 个、首次返回最多 4 个会话块。
它们是带版本的服务端 profile 参数，不直接堆进用户设置页；评估后再确定默认值。
这些参数控制成本，不能成为“名单已经完整”或“这是目标批次”的依据。

### 6.2 自动展开

以 current 已授权消息集合为边界，按以下顺序补充：

1. **命中消息完整正文**，避免只返回命中 chunk。
2. **确定的回复目标与线程根**，最多回溯 8 层；检测循环、缺失及跨范围关系。
3. **邻近消息**，起始建议前后各 4 条；邻接消息无需再次通过原 query 的相关性门槛。
4. **后续读取线索**，指出还有已授权的后续内容可读；不能因为离命中远就默认忽略最终更正。

关系状态为 unknown 时，退回时间邻接，并标明只是邻接而非已确认的问答链。
时间窗口不是可靠话题分割：一条群聊里可能混着多个话题，不能把所有相邻消息视为因果关系。
按来源时间加稳定唯一键排序；同时间无法证明先后时不得编造因果顺序。

### 6.3 合并与排序

- 同 canonical 会话下有重叠消息的窗口合并，每个 Event/hash 只返回一份正文。
- 不重叠的窗口可同属一个会话但必须保留中间缺口，不能拼成连续原话。
- 不跨会话自动合并；跨会话关系只能作为显式引用。
- 会话块之间按相关性排序，块内按时间排序；保留 `hit`、`reply_target`、
  `thread_root`、`neighbor`、`followup` 等选择原因。
- actor 标识和原始角色来自源记录；不要把所有来源 actor 强行改写成聊天模型的 user/assistant。

### 6.4 “最终决定”与后续撤销

前后 4 条无法保证捕获跨天撤销。首版明确采取如下方式：

- 工具可接受可选 `intent=latest_state`；默认 `evidence`。意图改变读取策略，不放松权限或扩大调用方的硬过滤。
- `latest_state` 在命中窗口之外，尝试追加该会话授权范围内的近期尾部窗口；不连续时单独成块并标记中间未读范围。
- Agent 应通过会话内再次搜索、向后续读检查变更。不能用“取消/修改”几个关键词证明没有反例。
- 仍有未读范围时，回答只能表述“在已读取的材料中”；不能给出无条件的“最终/唯一/全部”断言。
- “某天讨论了什么”可以使用消息时间过滤；这仍是 current 文本阅读，
  **不等于恢复当日尚未修订的历史版本**，后者不在首版。

客户问“截至某天的业务状态”时，只有业务源有明确历史查询能力才可按该时点回答。
业务历史查询不等于开放 Context 的 as-of；若数据源只保存当前状态，必须说明不能还原历史。

## 7. 预算与超长消息

### 7.1 不再独立裁掉每一条消息

对每个命中形成最小解释组：命中消息 + 能获得的关键回复目标。
在预算不足时，优先减少会话数或普通邻居，不应留下“就这么做”却把“怎么做”裁掉。
无法容纳最小解释组时，必须返回明确的 `budget_exhausted` 或部分证据状态和续读入口。

同样不能把“完整对话组”变成无限预算豁免；最终正文、元数据、引用、完整性说明和工具包装都计入响应预算。

建议实验预算：

| 项目 | 起始建议 | 性质 |
| --- | --- | --- |
| 首次内容 token 预算 | 8000 | 沿用现有量级，需预留引用/结构开销 |
| 单次完整序列化输出 | 64 KiB，上限 256 KiB | 可精确执行的 UTF-8 字节硬上限 |
| 消息数量 | 默认 40，上限 100 | 防止大量极短消息的结构开销失控 |
| 自动续读 | 最多 3 次，累计 24000 预算 token | Agent 适配层的初始策略，不是强制每次读满 |
| 任务级补证与查询 | 最多 2 次补充搜索、3 次续读、4 次业务调用（含分页/重试），累计 24000 输入证据预算 token | 初始端到端上限；身份查找也计入业务调用，不能靠子任务重置计数 |
| 单次服务 deadline | 10 秒起步评估 | 超时显式返回，不能装成空结果；冷启动单独测量 |

首次检索、续读和业务结果共用任务证据预算；对话全文已占满预算时不能再无限追加数据库行。
编排器另设任务总时限，首轮建议 60 秒用于正常热态评估；超过时限应留下可诊断任务状态，
不是换个子调用继续无限运行。具体额度按主场景成功率/延迟实测调整后冻结。

当前 Event 的 token 估计存在按字符长度估算的路径，不能声称已严格符合任意消费模型 tokenizer。
新增协议必须报告计数方式和 tokenizer/profile：

- 已知并支持消费模型 tokenizer：对最终序列化内容精确计数后装配。
- 未知 tokenizer：标记 `estimated`，采用保守估计并执行字节硬上限；
  Agent 适配层为 system prompt、工具定义和回答预留空间，发送给模型前再次计数。
- 不把 Embedding tokenizer 的 8192 窗口当成消费 LLM 的上下文窗口。

### 7.2 超长单条消息

不能因单条消息放不下就永久无法阅读，也不能静默截掉末尾：

- 常规优先返回整条；超长消息按段落/句子边界分页，必要时退回明确的 Unicode code point 范围。
- 返回原 Event/hash、总长度、当前范围和消息级 continuation handle；
  它仍是一个 Event 的部分证据，不新增伪造的 Event。
- 命中定位的 UTF-16 offset 与输出 code point 范围必须显式转换，不能混用。
- 部分内容标记 `partial`，引用绑定到 Event/hash + 范围；摘要不能冒充缺失原文。
- `read_context` 的消息级句柄继续读该消息，避免跳过它后只推进会话游标。

这需要对现有完整 Event item 合同作版本化扩展，不能把部分正文偷偷放进旧的“完整消息”字段。

## 8. 客服任务、Agent 工具与结果合同

下列为语义草案；具体 HTTP route、schema 名称和字段在实施 PR 中确认。

### 8.1 请求

```text
search_context(
  task_handle,               # 受信任入口绑定发起消息、会话及授权范围
  query,
  objective?,                # 当前缺口：批次/名单/字段含义/变更；不是授权参数
  filters?,                  # source/conversation/time；沿用已验证语义
  intent?: evidence | latest_state,
  budget?
)

read_context(
  continuation_handle,      # 服务端签发；可指向会话或消息范围
  budget?                   # 只能在服务端上限内调整
)
```

consumer、reasoning purpose、org 和 principal 由受信任入口绑定。
客户端不能用任意 `org_id` 或 `allowed_uses` 自授访问/推理权限。
个人版本是代表 owner 工作，不声称每个 Agent 已具备独立的组织身份。

`read_context` 不接受任意 SQL、Blob 路径或对其他会话的 cursor 改写。
工具 schema 必须严格拒绝未知参数、无效预算和无效句柄。
客服入口必须携带并验证 source message ID/hash、canonical conversation 和收到问题的时间；
自由文本测试可显式无锚点，但不得因此自动取得客户/项目绑定。task_handle 在后续调用中沿用相同约束。

### 8.2 结果语义

扩展现有 ContextBundle，使用一个规范化的正文/证据列表；会话窗口只引用 item/citation ID，
避免同一消息在 `bundle` 与 `windows` 中复制两份而浪费预算。

| 字段组 | 必要信息 |
| --- | --- |
| 读取身份 | schema/profile 版本、snapshot ID、authorized read epoch、consumer/purpose |
| 消息证据 | Event/hash、source、canonical conversation、actor、occurred_at、正文或显式部分范围 |
| 对话窗口 | 顺序、命中项、展开项及原因、窗口间是否连续 |
| 检索信息 | hybrid/lexical、已授权范围的索引 coverage、降级与排除原因 |
| 完整性 | 当前页是否完整、前后可续读状态、关系是否可解、文本缺口、来源同步范围状态 |
| 预算 | 输出字节、token 计数方式/数值、选择/省略数、使用的 budget profile |
| 续读 | 不透明句柄、方向/用途提示、到期时间 |
| 引用 | 可稳定解析的 citation ID，绑定 snapshot、Event/hash 及正文范围 |

Agent 可读的检索输出示意，**不是完整的客服任务合同或已经存在的 JSON schema**：

```text
读取范围：当前已同步且已授权的消息；源平台历史完整性未知。
会话 A / 窗口 1：
  [e1] 甲 09:00（回复目标）：方案 A ...；方案 B ...
  [e2] 乙 09:02（邻近）：客户必须要离线能力。
  [e3] 甲 09:03（命中）：那就按第二个方案。
  后面还有可读消息：handle_after_1

如果问题问的是最终方案，请继续检查后续内容。
```

### 8.3 “完整”必须分层表达

不能只有一个 `complete: true`：

1. **消息内容完整性**：整条/部分/不可物化。
2. **本地读取范围完整性**：所声明授权范围内是否还有未返回消息；到达边界不代表整个会话已读完。
3. **关系完整性**：回复目标已解析或 unknown；不能从不可访问目标的存在泄露身份/数量。
4. **来源同步完整性**：complete / partial / unknown，只有 connector 已有可靠覆盖证据时才能标为 complete。
5. **问题证据充分性**：服务端只提供可验证信号；Agent 的充分性判断不是事实完整保证。

全文已同步不代表每条可读；索引覆盖也不代表全文同步。
来源覆盖元数据只返回当前授权范围内可见的状态，不通过缺口、计数或 cursor 泄露未授权消息。

### 8.4 CustomerTaskBrief：交给 Cursor 的不是一段无依据摘要

brief 引用 bundle items，不重复存放全部原文；版本化保存核验结果及剩余缺口。

| 字段组 | 必要信息与约束 |
| --- | --- |
| 任务来源 | task ID、brief version、原始问题、发起 Event/hash、会话、收到时间、回复目标 |
| 业务范围 | 经验证的客户/项目/批次 ID；绑定依据；候选不能混入已确认字段 |
| 问题解释 | intent、需要的状态字段、查询时点；每项 verified/candidate/unresolved/conflicting |
| 对象集合 | 预期数量及其依据、已确认成员、业务 ID/别名映射出处、未匹配/多匹配项、集合是否闭合 |
| 待查事实 | 字段语义、业务权威源、时间约束、允许返回字段；不能携带任意可执行 SQL |
| 证据 | 原文 citation IDs、名单变更链、相关 snapshots、可见范围内的未读/不可读缺口 |
| 路由与治理 | 内部分析/客户输出分级、范围与预算引用、需要澄清/人工核实的原因 |

字段确认不能仅来自 LLM 输出；精确 ID、名单和状态须可绑定到原文或受控业务查找结果。
一个字段有多个互斥候选时保留 conflict，不用取最高相似度或“高置信度”解决业务歧义。

示意流程：问题提到 6 位，brief 已解析 5 个 ID、另 1 个别名多匹配，
此时应请求定向身份查找；查找仍不确定则生成最小澄清问题，禁止直接查询任意第六人填满列表。

### 8.5 BusinessEvidence：查询结果也必须可引用

由受控工具/执行通道记录查询证据，不能仅接收 Cursor 自述“已查询数据库”：

- task/brief version、query ID、工具/数据源 ID、实际强制执行的业务范围与参数摘要；
- 对象稳定 ID、返回字段及业务值、记录主键、版本/更新时间、查询时间；
- 结果是完整还是分页/截断；显式区分 `found`、`not_found`、`ambiguous`、
  `permission_denied`、`unavailable`，`found` 中的业务状态允许 unknown；
- 业务字段客户可见性、权威来源规则、可供内部核验的 citation ID；
- 不回传凭据、无关客户行、整表快照或未经必要性筛选的敏感字段。

内部引用可指向受保护的查询结果记录，不强制把业务结果伪装成原始聊天 Event。
用于对外答复的事实与内部审核引用分离；客户不应收到数据库主键、内部工具地址或内部聊天全文。
如目标 Cursor 通道不能返回结构化工具结果和可核验出处，应补齐适配或保持人工验证，不能用自由文本替代已核验事实。

### 8.6 回复草稿合同

草稿保存 customer-facing text、逐项 claim → evidence 映射、对象覆盖表、时点和未解决问题，
并关联 brief/query versions 与审核状态。对“都/全部”这样的集合结论，必须有完整集合及逐项有效状态依据。
客户可见正文不自动包含内部证据或推理过程；审核界面能查看依据和被剔除的敏感字段。

## 9. 一致性、续读与缓存

### 9.1 单次调用

- 采用同一授权和 current 生命周期视图选择种子、邻居与关系目标。
- 读取选中正文后校验 Event/hash 和版本边界，再保存 snapshot/bundle。
- 可复用现有 source boundary 检测；变化时最多重试一次，仍变化则显式要求重试，
  不返回混合版本的“成功结果”。
- 不能长时间持有跨 Agent 调用的 SQLite 读事务。

### 9.2 续读句柄

建议首版采用服务端短期记录 + 高熵不透明 ID，默认 TTL 30 分钟，并限制每个 consumer
的句柄数量和总存储；无业务必要不持久化额外正文副本。
绑定 principal、consumer/purpose、过滤范围、会话/消息身份、方向、稳定排序边界、profile 和读取版本。
知道句柄不等于授权，每次调用仍检查当前权限。

首版采取**安全优先的变化即失效策略**：

- 沿用已有 Authority/policy 边界版本；无法证明原范围未变化时，返回统一的
  `context_changed`，不续用旧数据。不得在错误中暴露隐藏资源身份。
- 到期返回 `cursor_expired`；伪造/跨 principal 使用返回不泄露目标存在性的错误。
- 数据未变化时用 keyset 分页，避免 offset 分页重复/漏读。
- 每次读取形成新的不可变 snapshot，并关联上一页；引用始终指向实际提供的版本。

全局 Authority epoch 在活跃库中可能使无关更新也导致失效，这是已知成本。
后续可增加授权范围的会话版本指纹以减少误失效，但必须检测新插入、修订、删除和权限变化，
不能只 hash 已返回消息。首版需测量高写入场景，失效率不可接受则在上线前升级此设计。

历史快照 replay 与“继续读取 current”是不同操作，不能用 replay 绕过删除或权限收回。
已交付到外部 Agent 的文本无法被服务端收回；适配层发现变化后应重新组装并替换旧证据，
最终回答前校验已使用引用是否仍有效，无法校验时明确标注。

### 9.3 跨聊天与业务库的时间边界

Context snapshot 与业务数据库不是同一事务，不宣称获得跨系统全局一致快照。
brief 固定解释依据及目标时点，业务结果记录 queried_at、record_updated_at/version。
字段新鲜度规则由业务配置定义，而不是统一认定数据库或最新聊天永远优先。

生成草稿及实际发送前，检查发起问题/名单版本、客户可见规则与关键业务结果是否仍有效。
若发生替换、撤销、权限变化或超过新鲜度窗口，草稿转为待重新查询/审核；已批准文本不能静默替换后发送。
业务源没有版本/变更检测能力时，只能声明“截至本次查询”，根据风险要求人工确认，不能标记为实时一致。

### 9.4 不可信内容与隐私

- 原文仅作为 evidence data，不得提升为 system 指令、工具授权或自动执行代码。
- 先鉴权、再扩展和计数；不能用一个可见命中替邻居或父消息授予权限。
- 不把原始错误、正文、连接器 token 写入诊断；默认日志记录阶段、计数、耗时和安全原因码。
- 导出/适配器继续遵循相同用途与授权，不新增“方便 Agent 用”的全库后门。
- 内部分析权限不等于对客户发布权限；字段/证据按业务配置分级，未知分级默认不对外披露。
- 对外最小必要输出、规则过滤与人工确认共同承担发布控制，不能仅靠模型自行判断“这条不敏感”。
- Cursor 使用远端模型或工具时，数据出站必须符合另行授权的部署策略；“Embedding 本地运行”不代表整个客服链路都在本机。

## 10. 关系、正文和性能前置工作

### 10.1 对话关系投影

复用 IngestRecord 的来源语义，明确 `reply_to`、`thread_root` 与 revision lineage 的差别。
关系先绑定带来源命名空间的外部身份，再在授权 current 读取中解析到目标 Event。
目标尚未采集、被删除、不可见或无法确定时保留安全的 unresolved 状态，不猜测、不自动拉远端。

首版只支持确实提供并成功保留关系的来源；其他来源明确降级为邻接窗口。
必要的持久化字段/投影变更需迁移和旧库回放测试，不为方便展开改写原始 Event。
原生 scope（大群）与原生 thread（话题）不能混为一个“完整对话”。

### 10.2 来源文本无效不是展开能自动修复的问题

目前 `input_invalid` 合并了空正文、编码、hash、封装和请求协议等失败。
对截图中的隔离任务，不能未经诊断便假定都是空消息。

建议增加安全的内部原因码，并映射成可操作的聚合诊断：

- 合法但没有可索引文本，如仅附件：区分“不适用”与损坏；不生成伪正文填充索引。
- 有正文但提取失败：修复提取器，补充 fixture；按现有投影重建流程恢复。
- 编码/hash/内容封装失败：作为数据完整性问题处理，不能让 grep 绕过校验。
- 模型输入协议错误：修复服务/客户端，而非让用户编辑原消息。

这类改动会影响索引分母和状态机，必须单独定义迁移语义，不能只改 UI 百分比。
展开碰到不可读消息时给出当前授权范围内的材料缺口；不能把缺口当成零条消息并宣称连续。
遇到存储不可用等系统性错误则显式失败，不以“部分成功”掩盖整个数据源故障。

### 10.3 防止读取放大

初版可以在已有的授权元数据视图中展开，但不能为每个命中再扫描/物化全库正文。
会话索引、邻接读取应在 Authority adapter 边界提供；对同一批窗口批量取正文。

需特别注意：当前 ContextEngine 会在检索前物化生命周期候选。仅新增 Expander
并不能宣称整体已变成“只加载命中正文”。实施时应先测量该路径，再按 adapter 能力拆出
metadata-first 与 bounded materialization；拆分前后必须通过相同权限和生命周期测试。

现有 lexical fallback 若必须扫描更多正文，应声明成本并设置上限。
超出扫描/时间上限时返回明确降级/截断信息，不能报“没有相关结果”。
所有缓存键绑定用途、policy、读取版本和 profile；原文响应遵守当前缓存生命周期。

## 11. P0 客服编排、覆盖核验与人工确认

### 11.1 有界问题补全与查询循环

1. 验证发起消息和业务范围，建立任务和待补槽位；不是只转发一句问题给 Cursor。
2. Cursor 根据缺口调用 `search_context` / `read_context`，查找批次、名单、字段含义及后续变更。
3. 对身份/批次歧义调用受限业务查找；形成带证据的 brief。关键参数仍不确定时先澄清，不抢跑状态查询。
4. 在已核验范围内按稳定 ID 查询必要业务字段，收集结构化 BusinessEvidence；正常路径优先批量查询，避免一人一次的低效调用。
5. 检查对象覆盖、结果完整性、字段权威性、时效与矛盾；可补证时继续，受任务总预算约束。
6. 生成对客户可见的草稿和内部证据表；正常情况进入人工确认，歧义/冲突/不可用进入明确分支。

Cursor 可以提出查询计划，但只有工具结果和证据校验可以推进任务状态。
不需要先建第二个泛化规划 Agent；先让目标 Cursor 运行在同一份明确合同和有界工具循环中。

### 11.2 覆盖与冲突规则

- 以已确认名单为基准，逐项记录身份解析与结果状态；每人多条业务记录也要按批次/任务限定，不能跨项目选最新一条。
- `not_found` 不等于“未回复”，`unavailable` 不等于“没有”；分页未完成不能用于集合否定判断。
- 业务值为 unknown、状态语义未明确或字段相互冲突时，不生成未经限定的确定结论。
- 按字段权威来源配置比较聊天与业务记录的有效时点；不能规定“永远信数据库”或“永远信最新聊天”。
- 证据存在校验和结论支持校验分开：不能用“有 citation”掩盖“引用并不支持这句话”。
- 可独立确认的部分可给出限定草稿；但不得把剩余对象状态补成默认值，也不得以部分结果回答“全部”。

### 11.3 人工确认与发送

首版沿用现有消息发送能力，但新增明确的草稿审核门槛：展示回复目标、客户可见文本、逐对象依据与剩余缺口。
必须由授权客服确认后才能发送；人工编辑后的文本仍需重新检查可见性和明显事实冲突。
发送需幂等，重试不能重复回复客户；失败保留待处理状态而不是宣告已回复。

“哪一批 6 位？”之类的澄清消息也先作为草稿审核，不在低置信度时自动向客户连续追问。
审批等待期间发生重要变化时令草稿失效，重新核验再审批，不能把旧批准复用于新版答案。

现有 `/ask` 继续保持单次 assemble + completion 语义，不静默升级成数据库查询或多轮客服。
P0 使用独立显式任务/profile，自动续读、业务查询和审核状态由新适配层治理。

## 12. 以客服闭环为优先的实施拆分与兼容性

按要求合并为 **1 个完整 PR**，内部仍按五个可验证里程碑推进，不能用单 PR 跳过依赖和验收。

| 里程碑 | 内容 | P0 可验收交付 |
| --- | --- | --- |
| 1：任务合同与接入 | 发起消息/客户范围、brief/业务证据/草稿状态合同、Authority 持久化、HTTP 只读业务合同 | 可持久恢复任务；缺少业务 URL 时明确失败 |
| 2：问题缺口驱动读取 | canonical 会话、原生回复映射、授权检索展开、窗口/预算、续读句柄 | 给定原问题找出名单确认和相关回复目标，不误用 revision |
| 3：问题补全与业务查询 | MCP 有界补证、批次/名单/字段消歧、稳定身份、结构化查询结果和版本绑定 | “上次六位”只查询经核验对象，工具层拒绝范围外对象/字段 |
| 4：回复核验与人工确认 | 集合覆盖、时效复查、客户可见性、claim→evidence、桌面审核、发送幂等 | 未批准不发送；内部字段不能进入受支持 claim；变化后批准失效 |
| 5：端到端验收与文档 | 合成客服 fixture、MCP/API/SQLite/桌面构建、故障与兼容回归、配置说明 | 所有检查在同一 PR 完成后再提交 |

五个里程碑必须在该 PR 内全部完成；评审可按提交或文件分层查看，但不拆成多个 PR。

非主链路的 UI 美化、完整索引状态机重设计、通用适配平台和大规模 ANN 延后。
影响名单证据读取的文本提取问题必须修复或作为阻塞显式呈现，不能为了“P0”静默绕过。

### 兼容与发布

- 旧 `/search`、`/search/source` 和桌面 snippet 格式保持不变，避免破坏现有客户端。
- 新能力使用显式版本/profile；不把旧 `display` 快照原地改成 `reason`。
- 复用现有消息/分块向量，原则上不需要重新下载模型或全库重新 embedding；
  新关系投影可能需要单独 backfill，缺失来源字段的旧数据仍须报告 unknown。
- 先个人 SQLite；设计可扩展不等于组织版本已经交付。
- 业务源作为受控外部查询接入，不把业务库迁入个人 SQLite；个人 owner 权限不自动授予客户项目数据访问或对外披露权。
- 客服 profile 独立开关，关闭后停止新自动任务并保留人工路径；未审批草稿不能因为回滚被发送。
- 灰度时同时记录旧检索结果与新组装的非正文指标；关闭新 profile 即可回退旧路径，
  不删除已有 Event、成功向量或旧 snapshot。
- 本 PR 不读取或修改真实用户业务数据；真实业务接入由部署方提供受控 URL 和只读授权。

## 13. 以客服任务成功为核心的验收计划

以下为拟议发布门槛，尚未运行或达到；评审时可调整，但必须在调参前冻结评测集和口径。

### 13.1 数据与对照

冻结的保留集至少 60 个独立客服任务：建议 40 个依据充分的正常可解任务、20 个必须澄清/转人工的异常任务，
开发集另建；不得把同一客户/项目/名单批次的关联会话或问题改写拆到不同集合造成泄漏。
每例标注原始发起消息、客户/项目/批次、名单及变更、业务身份映射、字段语义、
模拟业务表/查询时点、允许的查询范围、预期结论和可见字段、正确分支与禁止返回内容。
另保留通用对话展开组件集；组件集通过不能替代客服任务集通过。
真实个人数据必须另行授权；默认使用合成或明确脱敏数据。

对照四种方式：现有 snippets、仅增大 top-k、固定邻近窗口、本文方案。
所有方式使用相同语料、业务数据、授权、消费模型、总预算和问题，仅改变上下文策略，
不能通过多给 token、预先提供名单或让某一组访问更多业务字段制造提升。
必须记录全链路调用和数据版本；真实 Cursor/业务工具集成验证与可复现 fixture 评测分开报告。

| 场景 | 要证明的行为 |
| --- | --- |
| “上次选中的 6 位” | 找对批次、有效名单、状态含义和稳定 ID，逐项查询核验，而非只找到六个名字 |
| “执行中的几位”与“上次六位”同屏 | 不默认是同一集合，不被邻近展示误导 |
| 两个项目/批次有相同人数、同名人员 | 项目与身份消歧正确，无法确定时澄清，不跨客户查询 |
| 名单替换、取消一位、补选一位 | 正确解释目标时点的成员集合，不混用旧名单和当前状态 |
| 六人只查到五人、结果分页未完 | 不把缺失/未读当未回复，不产生不实“全部”结论 |
| 回复/谈价/合作/交付状态混用 | 按字段定义回答，不能将“未交付”说成“未回复” |
| 业务库与聊天矛盾、历史状态不可查 | 按字段权威和时点核验，无法解决则说明不足/转人工 |
| 内部备注、敏感报价、他客记录 | 授权分析与对客披露分离，范围/字段约束可验证 |
| Cursor 工具不可达、DB 超时/拒绝访问 | 不假装已查询，不生成成功式业务状态 |
| 审批期间状态变更、重复发送请求 | 草稿失效与重审有效，未批准不发送，批准发送幂等 |
| “第二个方案/这样做” | 找到解释指代的原文，不单引孤立回复 |
| 后续撤销/条件变化 | 覆盖关键更正，或明确后续未读，不能给出未经限定的旧结论 |
| 同群多话题、跨会话同名 | 不混淆会话/回复链，不把邻接当因果 |
| 短会话、超长单条、千条会话 | 短的可完整读，长的可连续分页且预算有界 |
| 修订/tombstone/读取中更新 | 不返回旧 current 内容；续读正确失效 |
| 重复时间戳、乱序到达 | 稳定排序，无重复/遗漏，无法证实顺序时不捏造 |
| 空白/附件-only/坏编码/hash | 正确分类或缺口，不能伪造正文 |
| 精确错误码与中文同义问法 | 保留词法优势和语义召回能力 |
| 无关问题/无答案/互相矛盾 | 不因扩展更多文本而强行编答案 |
| 权限/游标伪造/恶意原文指令 | 无越权正文及元数据泄露，不执行证据中的命令 |
| 模型离线、索引不全、正文存储失败 | 显式降级或失败，不伪装成完整结果 |
| 源历史部分同步 | 本地结束不能被标为源平台全历史完整 |

### 13.2 度量与门槛

**P0 主门槛优先于检索分数。以下比例以固定保留集为分母，不能删除失败例，也不能用全部转人工换取准确率。**

- **正常任务端到端成功率至少 90%**：在正常可解子集内，同时满足正确项目/批次/名单、正确查询、
  完整覆盖、事实受证据支持及对客可见性；只生成草稿不算通过，须能在测试通道经审批发送一次。
- **正常任务不必要澄清/转人工率不超过 10%**：事实可解但系统未完成的例子仍计为端到端失败，
  与规定的人类“发送审批”不是一回事。
- **异常任务正确分流率至少 95%**：在异常子集内按标注要求提出最小澄清/转人工/显式失败，
  不把无记录、未知、权限拒绝、工具错误解释成未回复。
- **严重错误零容忍（固定测试集）**：跨客户/项目查询或披露、虚构成员/状态、已知漏项却回答“全部”、
  未批准发送、重复发送例数为 0；不能用平均正确率抵消。
- **成员集合和查询覆盖分别报告**：集合 exact match、身份映射准确率、全部成员有效状态覆盖率；
  预期名单已错时“查完所选 ID”不能算完整覆盖成功。
- **执行可核验**：P0 最终验收必须有真实目标 Cursor、已授权只读业务测试源及实际工具结果记录。
  mock 可测试故障分支，不可替代集成证明；未获生产数据授权不阻塞 synthetic 开发，但实际业务覆盖声明须受限。

支撑能力继续满足：

- **硬不变量测试全部通过**：授权隔离、生命周期、引用绑定、游标、输出字节/已声明 token 计数上限。
- **证据集合完整命中率**：在规定总预算/调用上限内，包含某例全部必要证据的比例；
  初始目标至少 90%，不能只用“命中任意一条”替代。
- **关键更正处理**：保留集内有必要更正却只返回旧结论、且未说明缺口的例数为 0。
- **定位保持率**：首阶段必要消息 recall 相对原检索不得下降超过 2 个百分点；
  展开策略不应把已有有效命中挤掉却无解释。
- **完整性诚实性**：有限测试集上，已知缺口却报告完整的例数为 0；
  不可见数据不得通过缺口计数暴露。
- **回答支持度**：固定消费模型，逐条评估主要结论是否由所引原文支持，
  或由所引有效业务结果支持，目标至少 95%；模型裁判只能辅助，错误/争议例由人工复核。
- **效率**：报告总 tool calls、累计输出 token/字节、重复正文比例、正文读取量、
  检索/展开/业务查询/推理分别耗时及 p50/p95，并报告问题到草稿的端到端延迟，
  人工审批等待单独统计，不用一次小样本耗时代替。

性能用 1k/10k/更大已授权消息规模与短/长会话分别测量，标明 CPU、内存、冷/热状态、
向量覆盖和并发写入负载。首轮建立基线后再冻结毫秒级 SLO；
上线前不得在默认范围内出现无界扫描、多命中重复全库物化或无上限重试。
同时报告 Authority 更新导致的游标失效率；若常态负载下无法连续阅读，不能仅以“安全失效”视为验收通过。

## 14. 核心目标确认与下一步评审

用户已确认：**覆盖模拟人工客服场景是最高优先级。** 详细设计仍需评审，本次只修订方案。

本轮将以下事项明确列为 P0：

1. 以真实客户问题为入口，找准它指向的项目、批次、成员集合和业务语义。
